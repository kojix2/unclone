# 概要

我々は、Rust カーネルを用いて PyClone-VI [@gillis2020pyclonevi] を再実装した unclone [@unclone_github; @unclone_zenodo] を、8 コア / 16 スレッドの AMD Ryzen 7 5700X を搭載したワークステーションで評価した。両実装を NumPy で生成した同一の初期値から開始したところ、18 通りのデータセットとシードの組み合わせすべてで同一の変異分割が得られ、調整ランド指数（ARI）は 1.0 であった。細胞存在率（CCF）の最大絶対差は $5.5\times10^{-13}$ であった。1 スレッドでは、100〜2,440 変異の入力に対して unclone は PyClone-VI より 2.8〜5.9 倍高速であった。unclone の所要時間には CLI の起動時間が含まれる一方、PyClone-VI はウォームアップ済みの Python プロセス内で計測した。全 2,440 変異を含む TRACERx 入力に対し、unclone カーネルは 1 スレッド時と比べて、8 物理コアで 4.80 倍、16 ハードウェアスレッドで 5.10 倍の高速化を達成した。PyClone-VI の高速化率は最大でも 1.07 倍であった。8 スレッド時の同入力に対するレイテンシは、unclone CLI で 0.084 秒、ウォームアップ済みのプロセス内 PyClone-VI で 1.723 秒であった。ピーク常駐メモリ使用量（RSS）の中央値は、それぞれ 33.4 MB と 280.1 MB であった。

# 手法

## 実装とデータ

unclone は `make build release=1 cpu=native` でビルドした。計測対象の Rust ソース差分について、その基点コミットと SHA-256 ハッシュを `data/environment.json` に記録した。PyClone-VI 0.2.0 は上流コミット `07306831a9a4` からインストールした。入力データには公式の合成データおよび TRACERx のサンプルファイルを用いた。PyClone-VI は、いずれかのサンプルで観測されていない変異を破棄する。TRACERx 入力は、欠測のない 2,440 変異だけを残すよう一度フィルタリングし、このフィルタ済み入力を両実装で使用した。スケーリング計測のため、これらの変異のうち先頭の 100、250、500、1,000 個を含む、より小さな入力を作成した。生成した全入力の SHA-256 ハッシュも `data/environment.json` に記録した。

unclone カーネルはどのスレッド数でも同じ Rayon 実行パスを使用する。変分縮約と初期期待対数尤度は同じ行列積カーネルを共有する。CCF グリッド上で定数となるベータ二項項は観測ごとに 1 回だけ評価する。

両実装で同一の設定を使用した：ベータ二項分布、40 クラスタ、100 CCF グリッド点、精度 200、収束許容誤差 $10^{-6}$、最大 10,000 反復、1 回のリスタート、シード 7。数値比較では、シード 42 と 123 についても unclone の `--python-compatible` 初期化を使用した。

## 計測プロトコル

PyClone-VI の計測前に、Numba 関数をコンパイルするため、記録対象外のウォームアップを実行した。その後、PyClone-VI は単一の常駐プロセスで計測した。計測範囲には入力の読み込み、尤度の構築、初期化、推論を含め、結果の直列化は除外した。BLAS と Numba のスレッド数は、いずれも指定値に設定した。unclone は反復ごとに新しい CLI プロセスとして起動した。ツール間比較では、入出力を含む CLI 全体の経過時間を使用した。並列スケーリングでは、固定的な CLI オーバーヘッドがスケーリング計測に影響しないよう、Rust のプロファイリング境界で報告されるカーネル部分のみの時間を使用した。

各計測条件について、再現可能なランダム順序で 7 回ずつ反復した。中央値と四分位範囲（IQR）を報告する。1〜8 スレッドの実行は、それぞれ異なる物理コア 0 から $n-1$ に固定した。16 スレッドの実行では、8 コアすべてについて両方のハードウェアスレッドを使用した。ピーク常駐メモリ使用量（RSS）は、GNU `time` を用いて新たに起動した 3 つのプロセスで計測した。すべての生の観測値、要約、およびベンチマークドライバは、`paper/data` と `paper/scripts/benchmark.py` に収録している。

# 数値的一致

6 つの入力サイズを、それぞれ 3 つのシードで検証した。初期値を一致させた場合、すべての実行で ARI は 1.0 であった。CCF の相関係数は全実行で丸めると 1.0 となり、CCF の最大絶対差は $1.9\times10^{-14}$ から $5.5\times10^{-13}$ の範囲であった（表 2）。unclone は、浮動小数点精度に近い水準で PyClone-VI と数値的に一致した。ただし、この結果は、あらゆるプラットフォームや入力におけるビット単位の同一性を意味するものではない。

# 性能

## 1 スレッド比較

1 スレッドでは、unclone はすべての入力で PyClone-VI より高速であった。unclone の所要時間にはプロセスの起動と直列化が含まれる一方、PyClone-VI の所要時間にはプロセスの起動、JIT コンパイル、直列化のいずれも含まれない。中央値に基づく高速化率は 2.81 倍から 5.88 倍の範囲であった（図 1、表 3）。全 2,440 変異を含む TRACERx 入力では、レイテンシの中央値は unclone で 0.313 秒、PyClone-VI で 1.838 秒、IQR はそれぞれ 0.024 秒と 0.012 秒であった。

## マルチスレッドスケーリング

全 2,440 変異を含む TRACERx 入力に対し、unclone カーネルの性能はスレッド数の増加に伴って向上した（図 2）。1 スレッドに対するカーネルの高速化率は、2、4、8、16 スレッドでそれぞれ 1.52 倍、3.16 倍、4.80 倍、5.10 倍であった。8 コアでの並列効率は 60% であった。同時マルチスレッディングにより、カーネル時間は 8 スレッドの 0.061 秒から 16 スレッドの 0.057 秒へと短縮され、約 6% 改善した。性能は物理コア数付近で飽和する。相対的な高速化率が以前の実装より低いのは、1 スレッドでのカーネル時間が 56% 短縮されたためである。マルチスレッド時のレイテンシも、絶対値では改善した。

PyClone-VI では、スレッド数による性能向上がほとんど見られなかった。レイテンシの中央値は、すべてのスレッド数で 1.71〜1.84 秒の範囲であった。最良値を示した 4 スレッド時の中央値は、1 スレッド時より 1.07 倍高速であった。一方、16 スレッドでは 1.81 秒と遅くなった。この結果は、本ワークロードと、リンクされた OpenBLAS および Numba のバージョンに当てはまるものであり、他の PyClone-VI 入力にも一般化できるとは限らない。

## メモリ

1 スレッドでは、ピーク RSS の中央値は unclone で 32.7 MB、PyClone-VI で 277.0 MB であり、8.5 倍の差があった。8 スレッドでは、それぞれ 33.4 MB と 280.1 MB で、8.4 倍の差があった。この入力では、ワーカースレッドを追加しても、いずれの実装でもメモリ使用量はほとんど増加しなかった。

# 限界

本研究にはいくつかの限界がある。使用したのは、単一のマシン、単一のコンパイラビルド、上流で提供される 1 系列のサンプル、および実行時間の短いワークロードに限られる。計測中も動的周波数スケーリングは有効なままであった。計測順序のランダム化、CPU アフィニティ、および反復測定の中央値によって周波数変動や熱の影響は軽減されるが、完全には排除できない。小さな入力では、実行時間がプロセス起動時間に近づくため、計測値の相対的なばらつきが大きくなる。また、2 種類の比較では計測範囲が異なる。ツール間比較では、JIT を事前にウォームアップし、プロセス起動時間を除外しているため、PyClone-VI に有利な条件となっている。並列スケーリング比較では、より狭い、実装ごとに固有の計測範囲を使用している。これらの結果は、この特定の構成における再現可能な計測値であり、ハードウェアに依存しない普遍的な定数ではない。

# 結論

ローカルの 8 コアワークステーションにおいて、unclone は PyClone-VI の変異分割と CCF 推定を、機械精度に近い水準で再現した。1 スレッドでは 2.8〜5.9 倍高速であり、プロセスのメモリ使用量は約 8 分の 1 であった。unclone の Rust カーネルは 8 物理コアで 4.80 倍の高速化を達成したのに対し、PyClone-VI では同じワークロードでスレッド数による性能向上がほとんど見られなかった。同時マルチスレッディングによって、わずかながら追加の性能向上が得られた。これらの計測結果は、以前の 2 vCPU クラウド環境で得た結果を置き換え、両実装のマルチスレッド性能を明らかにするものである。
